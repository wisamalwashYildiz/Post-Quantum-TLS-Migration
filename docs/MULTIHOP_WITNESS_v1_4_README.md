# Post-Quantum TLS migration — v1.4 live three-hop receiving-endpoint corroboration

## Scientific boundary

This release **extends**, and does not replace, v1.1–v1.3. Three TLS-terminating receivers (`gateway`, `service-a`, `backend`) run in separate local Python processes. A client transaction traverses three actual TLS 1.3 connections. Every receiving process signs an observation of the transaction hash and negotiated handshake group. The same process also makes a signed forwarding report. A separate verifier checks the consistency of the path and the trusted receiver observations.

**This is not independent security isolation:** all receiving processes have the same Unix account and host trust domain. The receiver's witness signing key is assumed unavailable to the attacker. Report compromise is modeled by offline re-signing the adjacent forwarding reports with the report keys. The observer and report are both generated by the same receiving process; separation here is *between receiver processes*, not between each receiver and its local report issuer. Trusting a receiver remains an explicit assumption.

Connection identifiers are hashes of public TLS handshake randoms, *not* cryptographic TLS exporter bindings. Keys are generated per run and saved solely for offline lab verification. The application uses self-signed test certificates; it evaluates hybrid key exchange, NOT post-quantum authentication, PKI or production policy enforcement. v1.4 sends one transaction per TLS session. It does not retain v1.3 multi-transaction connection reuse.

## Dependencies

Requires existing project files `src/live_path.py` and `src/session_chain_v11.py` and its usual imports. Python SSL linked to OpenSSL >= 3.5 and an executable OpenSSL capable of creating a test cert. No pip dependencies beyond existing project.

## Within Ubuntu

Extract this archive into the existing project root first, merging `src/` and `tests/`, without deleting old files.

```bash
cd "/mnt/d/Articles/Post-Quantum TLS Migration/Post-Quantum TLS Migration-Project"
source "$HOME/pqc-research-venv/bin/activate"
OPENSSL_HOME="$HOME/opt/openssl-3.5.9"
export LD_LIBRARY_PATH="$OPENSSL_HOME/lib64${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
"$OPENSSL_HOME/bin/openssl" version
python -m unittest discover -s tests -p 'test_*.py' -v
python src/multihop_witness_v14.py \
  --openssl "$OPENSSL_HOME/bin/openssl" \
  --output results/multihop_witness_v14
python src/verify_multihop_witness_v14.py \
  --evidence results/multihop_witness_v14/multihop_witness.json \
  --keys results/multihop_witness_v14/lab_verifier_keys.json
```

Only run the verifier after the live capture succeeds. The `lab_verifier_keys.json` file is a secret and MUST NOT be uploaded, published, or reused beyond a local experiment. The public `multihop_witness.json` contains no signing keys.

## Local validation performed before packaging

- 10 new unittest cases passed (with existing v1.1 dependencies on the import path).
- A local OpenSSL 3.5.5 build with Python SSL 3.5.5 successfully executed two new end-to-end three-hop transactions, one fully hybrid and one with a classical middle hop. These runs are **independent local validation**, not a claim that a user Ubuntu 3.5.9 run has already completed.
- Fresh output produced: `valid=SATISFIED`, `classical_middle=VIOLATED`, `forged_baseline=SATISFIED`, `forged_corroborated=INVALID`, `missing_witness=UNRESOLVED`, `reassigned_witness=INVALID`.
- A separately invoked verifier reproduced `valid`, `classical_middle`, and `forged` verdicts.
- A caught and fixed simulation bug initially caused the forged report to mutate an aliased witness object. The final implementation deep-copies the modified session before re-signing. A unit regression verifies the receiver witness is unchanged by the attack.

## Future methodological necessities

A true zero-trust verifier would require independent OS identities or host separation, authenticated provenance for each receiving process, TLS exporter-based cryptographic channel binding where applicable, and realistic multi-request forwarding under concurrent flows. Do not claim full compromise resistance from these results.
